# 新产品创建规范

本文档是创建新的 Just VPN 产品时唯一的执行清单，覆盖项目复制、产品 code、INI 配置、协议映射、Swagger、前端文档、转移码和部署准备。

## 1. 产品隔离原则

1. 每个产品使用独立目录、独立 Git 仓库、独立远程仓库和独立服务器
2. 每个产品使用独立数据库。已有产品 ID 时数据库名使用完整产品 ID，例如 `id6752617299`；暂未分配产品 ID 时数据库名使用随机四位 code
3. Docker Compose 不需要为了产品改项目名。产品部署在不同服务器，容器名、端口和数据卷可保持模板默认值
4. 产品配置使用 `conf/app.ini`，配置格式固定为 INI，禁止改为 JSON、YAML 或硬编码配置
5. 本地覆盖配置使用 `conf/app.local.ini`，只在本地开发使用，必须被 Git 忽略。线上自动部署始终使用仓库中的 `conf/app.ini`
6. `docs/*.md` 是交付给前端或运维的本地文档，默认不提交 Git，唯独本文件作为母版规范随仓库提交
7. 新产品的产品差异只能写入 INI、映射 JSON、数据库运营数据、资源域名和前端文档。发现需要业务代码变更时，必须先完善 `just-vpn-origin`，验证后再创建新项目

## 2. 创建步骤

1. 从最新 `just-vpn-origin` 母版复制新目录。已有产品 ID 时目录名为 `just-vpn-<product_id>`；暂未分配产品 ID 时目录名为 `just-vpn-<code>`
2. 删除复制来源的 Git 远程地址，并绑定新产品自己的远程仓库：

   ```bash
   git remote remove origin
   git remote add origin git@github.com:JustGopher/just-vpn-<product_key>.git
   ```

3. 创建独立数据库。表结构由应用首次启动时的 GORM AutoMigrate 创建：

   ```sql
   CREATE DATABASE `<product_key>`
     CHARACTER SET utf8mb4
     COLLATE utf8mb4_unicode_ci;
   ```

4. 在 `conf/app.ini` 和 `conf/app.local.example.ini` 修改：
   - `Product`
   - `MappingFile`
   - `JwtSecret`
   - `InternalKey`
   - `[database] NAME`
5. 新建 `conf/mapping-<product_key>.json`，并删除复制来源的产品映射文件
6. 在映射 JSON 写入产品四位转移码 code、随机路由 namespace 和 Swagger 路径，完成映射、Swagger 和前端文档后再提交 Git

复制完成后，必须全局检查复制来源的产品 ID、数据库名、映射文件名、域名、转移码 code 和 Swagger 路径，确认没有残留：

```bash
rg -n '<来源产品ID>|<来源数据库名>|<来源四位code>' \
  --glob '!docs/**' --glob '!go.sum' .
```

## 3. 产品四位 Code 与路由 Namespace

### 产品四位 Code

产品四位 code 只用于转移码和中台项目匹配。已有完整产品 ID 时，code 由产品 ID 确定性生成。

算法固定如下：

1. 输入完整产品 ID，例如 `id6752617299`
2. 对完整字符串计算 `SHA-256`
3. 读取摘要前四个字节为无符号 32 位大端整数
4. 对 `26^4` 取模
5. 将结果转换为四位小写英文字母，字母表为 `abcdefghijklmnopqrstuvwxyz`，不足四位左侧补 `a`

该算法不暴露产品 ID，又能保证同一产品 ID 永远得到相同 code。

当前新产品结果：

| 产品 ID | 四位 code |
| --- | --- |
| `id6752617299` | `haxm` |
| `id6742070311` | `ymsy` |
| `id6758232183` | `lsdd` |
| `id6754278516` | `mjnu` |

创建产品时按上述算法计算一次，并写入映射 JSON 顶层的 `product_code`。该值上线后不得修改，后续即使调整路由也不会影响已发出的转移码。旧的已上线产品保持原有转移码前缀，避免破坏存量客户端。

### 暂无产品 ID 时

暂未分配产品 ID 时，直接随机生成四位小写英文字母 code，例如 `kqmf`。此时该 code 同时作为临时产品标识和数据库名：

```text
Product = kqmf
database name = kqmf
MappingFile = conf/mapping-kqmf.json
mapping product_code = kqmf
```

要求：

- 随机 code 必须检查中台现有项目、已有 VPN 项目目录和数据库，确保不重复
- 路由 namespace 仍需独立随机生成，不能直接复用该 code
- 未上线前如拿到正式产品 ID，可改为正式产品 ID、按算法重新生成 code，并同步重命名数据库、映射文件和仓库
- 已上线、已产生用户或已发出转移码后，code 和数据库名必须保持不变，即使之后补发正式产品 ID 也不再替换

### 路由 Namespace

每个新产品额外生成一个随机英文短单词作为路由 namespace，与四位 code 无关。

规则：

- 使用随机且有意义的英文短单词
- 最多 10 个 ASCII 字母
- 不使用产品 ID、四位 code、机械编号或无语义连续字符
- 不与任何已上线产品的 namespace 重复
- 生成后固定写入映射 JSON，不再自动变化

示例：

```text
product_id = id6752617299
transfer code = haxm
route namespace = nova
swagger path = /nova/6f4a9c2e
```

使用位置：

- 所有客户端 API 路由的首段，例如 `/nova/...`
- Swagger 页面路径，例如 `/nova/<hash>`
- 静态资源路径，例如 `/nova/resource/pop.png`
- 映射 JSON 中所有对客户端暴露的 `path`

四位 code 的使用位置：

- 延迟迁移弹窗返回的转移码前缀，例如 `haxm8f3k9q`
- 中台项目的 `code` 字段，用于按转移码找到来源项目

映射 JSON 顶层必须配置：

```json
{
  "product_code": "haxm",
  "swagger_path": "/nova/6f4a9c2e"
}
```

`product_code` 同时用于转移码前缀、日活 Redis 键和 `daily_stat.product_code`，不得在产品上线后修改。`swagger_path` 为仅开发环境开启的 Swagger 页面路径，必须以 `/` 开头。

创建产品前必须检查中台现有项目是否已有相同 code，且检查已有产品是否已经使用相同 namespace。由产品 ID 算出的四位 code 如发生极小概率碰撞，暂停创建并先调整统一算法与所有待创建产品；暂无产品 ID 时随机 code 重复则直接重新随机生成。

## 4. INI 与运行环境

`conf/app.ini` 至少确认以下配置：

```ini
[app]
Product = id6752617299
RunMode = prod
MappingFile = conf/mapping-id6752617299.json
JwtSecret = <当前产品独立密钥>
InternalKey = just.303

[database]
NAME = id6752617299

[redis]
HOST = redis:6379
```

暂未分配产品 ID 时，将示例中的 `id6752617299` 全部替换为随机四位 code。

约束：

- `RunMode` 只允许 `dev` 和 `prod`
- Swagger 仅在 `dev` 开启
- 所有时间使用中国大陆时区 `Asia/Shanghai`
- MySQL 使用独立产品库，Redis 可使用同一 Redis 实例但必须使用独立数据库或独立服务器部署方案
- Docker 使用命名数据卷，禁止挂载当前项目目录作为数据目录
- Redis 使用密码、AOF 和内存上限配置，线上参数以当前稳定 Compose 模板为准

## 5. 产品资源域名

每个产品的 OSS、S3 或其他备用资源域名必须独立准备，并放在该产品自己的 `docs/oss/`、`docs/s3/` 等目录中。域名文件加密后再交给客户端使用。

- 域名明文、加密文件和 iOS 解密说明必须属于当前产品，禁止沿用来源产品的域名或密钥
- 在交付前分别解密校验一次，确认得到完整且带 `http://` 或 `https://` 的地址
- 资源地址在接口响应、Swagger 示例和前端 Markdown 中必须替换为当前产品域名
- 密钥不得写入前端接口 Markdown、Swagger 示例或 Git 提交信息

## 6. 协议映射

### 基本原则

1. 后端业务代码始终使用原始协议，例如 `/api/v1/auto_login`、`device_no`、`vip_time`
2. 客户端只能看到映射后的路由、请求头和 JSON 字段
3. 映射改变名称，不改变 HTTP 方法、鉴权规则、字段类型和业务语义
4. 映射文件启动时读取、校验并编译到内存，请求期间不得读取 JSON 文件

### 路由

1. 所有客户端可调用接口都必须进入 `routes`，包括健康检查、登录、用户、系统、套餐、支付、节点、连接状态和静态资源
2. 每条客户端路由必须以该产品的随机 route namespace 开头
3. 除 namespace 外，路径语义也必须与其他产品不同，不能只替换前缀后保留同一组后续路径
4. 产品 ID 不得直接出现在路由中
5. 苹果通知与第三方支付回调属于服务端协议，可有独立映射路径，但不写进前端接口文档
6. 路径不固定为三段式。完整路径可混用 2 到 5 段，例如 `/<namespace>/ping`、`/<namespace>/auth/start`、`/<namespace>/system/release/check`、`/<namespace>/resource/image/fetch/*filepath`，避免整套接口机械保持同一长度或结构

### 核心字段词库

每个产品必须有独立的核心字段词库，不能只通过前后缀区分。至少以下字段必须与全部已存在产品比对后保持不同：

- 外层响应：`code`、`msg`、`result`
- 登录用户：`id`、`token`、`device_no`、`username`、`type`、`is_vip`、`vip_time`
- 公共请求：设备码、账号、密码、平台、版本、构建号、套餐、区域、节点、订单
- 高频业务：连接状态、流量、支付方式、交易号

当前三套新产品示例：

| 原始字段 | `id6752617299` | `id6742070311` | `id6758232183` |
| --- | --- | --- | --- |
| `code` | `acceptMark` | `outcomeFlag` | `returnCode` |
| `msg` | `captionText` | `noticeLine` | `hintLine` |
| `result` | `contentPack` | `payloadSet` | `replyData` |
| `token` | `permitKey` | `sessionSeal` | `authSeal` |
| `device_no` | `hardwareCode` | `installMark` | `deviceRef` |
| `is_vip` | `memberOpen` | `premiumReady` | `benefitLive` |

要求：

1. 映射词使用 lowerCamelCase，必须有语义，禁止 `axis000002` 这类流水号
2. 核心词中不要追加产品名、路由 code 或重复命名空间，例如不要写 `haxmStatusCode`
3. 相同原始业务字段在同一产品的所有请求、响应和嵌套 DTO 中必须使用同一个目标词
4. 不同产品的核心词不能相同，例如即使前后缀不同，`statusCode` 重复三次也不合格

### 字段前后缀

- `field_affix.prefix` 与 `field_affix.suffix` 是产品隔离层
- 映射 JSON 中只写核心词，不手写前后缀
- 加载器会统一展开前后缀，例如 `mi_`、`acceptMark`、`_go` 最终为 `mi_acceptMark_go`
- 默认使用下划线分隔。产品明确指定特殊格式时按指定格式执行
- 前缀和后缀必须使用有意义的英文短单词，每个最多 10 个 ASCII 字母
- 不使用产品 ID、四位 code、机械编号、超长缩写或无语义连续字符

### 请求与响应结构

- `request` 写原始请求字段到目标字段的对应关系
- `response` 必须按照真实响应 DTO 编写，外层 `code/msg/result` 和 `result` 内部字段都要映射
- 嵌套对象使用 `$field` 指定对象自身的目标字段，再列出其直接字段
- 不做无差别的任意 JSON 深度递归替换，只按已声明的请求结构和响应 DTO 映射
- 映射只替换键名，不替换普通字符串内容、URL 内容、业务文案或第三方数据值

## 7. 公共请求头

每个产品必须为以下原始请求头设计独立名称，并同步到映射文件、Swagger 和前端文档：

- `platform`
- `version`
- `build`
- `device_no`
- `client_time`
- `time_zone`

请求头只要符合 HTTP Header 命名规则即可，不强制使用 `X-` 前缀。例如可使用 `Platform-Key`、`Release-Note`、`Terminal-Mark`。不同产品避免整套复用相同请求头名称。

客户端本地时间使用 RFC3339 且带时区偏移，例如 `2026-07-11T20:30:15.123+08:00`。时区使用 IANA 名称，例如 `Asia/Shanghai`。

## 8. Swagger 与前端文档

1. Swagger 使用 `mapping.MapSwagger` 输出映射后的路径、请求头、请求字段和响应字段
2. Swagger 页面路径由映射 JSON 的 `swagger_path` 控制，必须在 `/<route namespace>/` 下并使用独立哈希尾段
3. `docs/API-<product_id>.md` 只记录该产品的客户端协议
4. Markdown 和 Swagger 示例中的静态资源地址、转移码前缀、请求头、字段前后缀必须使用当前产品配置
5. 前端文档不包含苹果服务端通知和第三方支付回调
6. 文档完成后至少检查：游客登录、注册、账号登录、初始化、套餐、支付、节点、心跳、断开和延迟迁移弹窗

## 9. 转移码与中台

1. 每个用户首次创建时生成 `四位 code + 六位随机字符` 的转移码
2. 转移码前缀固定为映射 JSON 的 `product_code`，不从路由 namespace 推导
3. 中台创建该产品时，已有产品 ID 则 `product_id` 使用完整产品 ID；暂无产品 ID 时临时使用四位 code。`code` 始终使用相同四位 code
4. 中台按转移码查询会员时，依靠项目 code 匹配来源项目，因此中台和 VPN 后端的 code 必须完全一致

## 10. 性能约束

- 映射 JSON、字段前后缀和路由表只在启动时加载到内存
- 请求字段使用内存中的直接映射查找
- 响应按 DTO 映射声明处理，避免全量反射和通用深层递归
- 只有压测确认映射成为瓶颈时，才为高频 DTO 生成专用转换函数

## 11. 上线前检查

- [ ] 新目录、独立 Git 仓库和远程仓库已准备
- [ ] `Product`、数据库名、JWT 密钥、`MappingFile` 已更新
- [ ] 来源产品的产品 ID、数据库名、映射文件、路由 namespace、域名和密钥均未残留
- [ ] 产品四位 code 已按产品 ID 算法生成，或在暂无产品 ID 时已随机生成，且未与中台已有项目冲突
- [ ] 随机 route namespace 已生成，且未与已有产品重复
- [ ] 映射 JSON 的所有客户端路由均以该 namespace 开头
- [ ] 映射 JSON 的 `product_code` 与中台项目 `code` 完全一致，不依赖路由 namespace
- [ ] 核心词库与已存在产品无重复
- [ ] 六个公共请求头已映射，且没有强制使用 `X-` 前缀
- [ ] 回调字段未映射，前端文档未收录回调
- [ ] Swagger、Markdown、静态资源示例均使用当前 route namespace，转移码示例使用当前产品四位 code
- [ ] OSS、S3 等资源域名已使用当前产品文件加密，并已完成解密校验
- [ ] `go test ./...`、映射 JSON 校验和 `git diff --check` 均通过
- [ ] 前端 Markdown 文档已检查，但未提交 Git
